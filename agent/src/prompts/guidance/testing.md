Testing conventions to follow (Vitest + Testing Library + Apollo MockedProvider):
- NEVER invent or assume the signature (parameter list, return type, exported name) of a function/hook you are testing. Use ONLY the exact signatures shown in the "Currently generated source files" section below. If a function you need is not shown there, do not call it with guessed arguments — write the test against what actually exists.
- Never query by a label/text/role that could legitimately match more than one element in the rendered tree (for example "Year" can appear both as a form field label and as a sort-control option). Before using getByLabelText/getByText/getByRole, check whether the exact same accessible name appears elsewhere in the component under test. If it might, scope the query with within(container) to the specific section, use getByRole(role, { name: /exact accessible name/i }) with a precise, non-overlapping name, or use getAllByLabelText(...)[index]/getAllByRole(...)[index] only when duplicates are expected and the index is deterministic.
- To mock an Apollo Client error response with MockedProvider, use { request, error: new Error('message') } — never { request, result: { errors: [...] } }. The result field's shape must always match the query's successful data type; GraphQL/network errors go in the separate error field, never inside result.
- Prefer role-based queries with a specific accessible name (getByRole('textbox', { name: /make/i })) over bare label/text queries whenever the component renders multiple similar controls (e.g. a form and a filter/sort bar on the same page). Remember the accessible role depends on the input's type: a plain text MUI TextField is role "textbox", but a TextField with type="number" renders <input type="number">, whose accessible role is "spinbutton", not "textbox" — use getByRole('spinbutton', { name: /year/i }) for numeric fields like a year input.
- MUI's sx prop compiles most static style values (borderRadius, display, padding, etc.) into CSS classes via Emotion, NOT inline style="..." attributes — only some dynamic/computed values (like a color derived from a runtime variable) may appear inline, and this is not guaranteed. NEVER query or assert against an element using container.querySelectorAll('[style*="..."]') or any raw inline-style/CSS string match. If a test needs to target a decorative or non-text element (e.g. a color swatch box) that has no natural role/label/text, add a stable data-testid attribute to that exact element when you write the component, and query it in the test with getByTestId/queryByTestId.
- Before finalizing a test file, mentally re-render the actual JSX/logic of the file under test and check for duplicate accessible names and correct call signatures among everything your queries and calls target.
